弃用死代理挂载与 SSH 隧道，构建真正“断网自愈”的 macOS × Lima 分流架构

原 AI 方案在核心方向（macOS 本地 sing-box 纯转发、零远端凭据、严格占用 1 个机场设备额度）上完全正确，但在系统代理挂载方式、跨虚拟机隧道稳定性、无感熔断降级与 macOS 权限模型四个底层工程环节存在致命盲区。本方案通过动态 PAC 软挂载 + 双向无状态 urltest 自动降级 + Lima 原生虚拟化端口映射，将“故障后手动点核弹按钮自救”升级为“Lima 卡死瞬间 0 秒自动回退直连”。

死代理残留断网窗口期：当本地 sing-box 或 Lima VM 异常退出时，基于本地 HTTP PAC 软挂载与 urltest 探针的架构可实现毫秒级自动直连回退，无需等待人工点击重置按钮。

核心定论 1：静态代理必死锁，PAC 软挂载天生防呆

原方案用 networksetup 强写静态 HTTP/SOCKS 代理，进程一死全网瘫痪。改用指向本地 http://127.0.0.1:7890/proxy.pac 的单行转发脚本，进程退出即刻触发 macOS 系统级 Fail-Open 直连。

核心定论 2：内建 urltest 探针，Lima 挂掉自动切直连

原方案中 to-lima 是写死的单向出口，Lima 重启或卡死会导致海外及 DNS 挂起。在 Mac 侧配置 urltest 聚合组，隧道不通时自动降级至 direct，不断网、不阻碍开启商用 VPN。

核心定论 3：弃用裸 SSH 进程，改用 Lima 原生 portForwards

Mac 休眠唤醒后裸 ssh -L 极易变成半开僵尸连接（端口在但包不通）。直接使用 Lima Guest Agent 原生 portForwards（基于 Virtio/vsock），随 VM 生命周期全自动愈合。

原 AI 方案的六大工程缺陷检核

原方案虽然设计了“三级恢复机制”，但它的底层思路是“先制造一个极易死锁的脆弱链路，再教你断网后怎么到处找按钮抢救”。在真实的 macOS 日常使用（频繁合盖休眠、Wi-Fi 切换、开启公司商用 VPN）中，以下六个隐患会频繁触发断网。

  1. 01 致命盲区：把静态系统代理当成唯一入口，人为制造“死代理断网”
    通过 macOS networksetup 将 Wi-Fi/以太网的 HTTP、HTTPS、SOCKS 代理写死为 127.0.0.1:7890 后，macOS 的 CFNetwork 栈是严格 Fail-Closed（失败即阻断）的。一旦本地 sing-box 崩溃或被误杀，所有浏览器、微信、终端及商用 VPN 客户端的登录握手都会直接报 ERR_PROXY_connection_FAILED。而如果你把系统代理设为自动代理配置（Auto Proxy Discovery / PAC URL）并指向 sing-box 内置的本地 HTTP 端点（仅返回一行 PROXY 127.0.0.1:7890; DIRECT，不做任何域名判断），当 sing-box 存活时流量全部进 sing-box 走 GeoSite/GeoIP 精准分流；当 sing-box 挂掉时，macOS 无法拉取 PAC URL 或执行 DIRECT 回退，天然实现 0 秒无感直连恢复。
  2. 02 链路脆弱点：单向死推 to-lima，缺乏 VM 宕机时的自动熔断（Auto-Failover）
    原方案规定 Mac 侧 sing-box 只有 direct 和 to-lima 两个出站，且未命中直连的流量硬编码推给 to-lima。当你在终端执行 limactl stop 或虚拟机内核卡死时，Mac 侧 sing-box 进程虽然还活着，但所有未命中直连的请求以及海外 DNS 解析会全部卡在 TCP 超时黑洞里。正确做法是在 Mac 侧 sing-box 中配置 sing-box URLTest 出站组，将 to-lima（设置高优先级或配合健康检查）与 direct 组合，或通过 Dock App 守护协程每 2 秒探测一次 127.0.0.1:17890 连通性，一旦 Lima 失联立即通过 Clash API (PUT /proxies/ProxySelector) 毫秒级热切换至 direct。
  3. 03 隧道隐患：手动维护 SSH 端口转发，合盖休眠后必现“僵尸半开连接”
    原方案架构图中采用“SSH 端口转发通道”将宿主机 127.0.0.1:17890 映射到虚拟机 10.203.0.1:17890。在 macOS 睡眠/唤醒（Sleep/Wake）周期中，SSH 进程极易处于进程存活但底层 Socket 假死的状态。事实上，Lima 官方端口转发机制（portForwards）直接在 lima.yaml 中通过 hostagent 利用 Apple Virtualization.framework 的 vzNAT / virtio-vsock 完成宿主机环回口到 Guest 内部端口的零开销桥接，根本不需要额外拉起 SSH 隧道进程。
  4. 04 权限与商用 VPN 冲突隐患：盲目执行重置会打断正在运行的企业 VPN
    在 macOS Sonoma / Sequoia 下，普通 GUI 应用或未提权脚本调用 networksetup -setwebproxystate 每次都会弹出系统管理员密码授权框（SecurityAgent），导致“< 0.5 秒极速重置”沦为空谈。更严重的是，许多企业级 VPN（如 Cisco AnyConnect、帕洛阿尔托 GlobalProtect、Tailscale）工作在 utun 虚拟网卡或自带 PAC/DNS 注入，原方案“无脑把所有网卡 PAC/Proxy 置 OFF”如果缺少精准过滤与 DNS 缓存刷新（dscacheutil -flushcache & killall -HUP mDNSResponder），会导致开启商用 VPN 后域名解析依然指向失效缓存。
  5. 05 DNS 污染与泄漏漏洞：只谈分流规则， completely 忽略了 Mac 侧 DNS 路由闭环
    原方案完全没有设计 Mac 侧 sing-box 的 DNS 模块。如果 Mac 侧 sing-box 直接使用本地运营商 DNS 解析海外域名，会遭到 DNS 污染并返回虚假 IP，进而误触发 GeoIP 规则导致代理失效；如果把所有 DNS 都扔给 Lima，一旦 Lima 停止运行，Mac 连百度和微信都解析不了。必须构建双栈隔离 DNS：国内域名（geosite-cn）强制走本地纯净 DoH/UDP（223.5.5.5），海外域名通过代理通道远端解析，且开启 independent_cache。
  6. 06 快照陈旧覆盖风险（Stale Snapshot Overwrite）
    原方案第一级恢复依赖开启代理前保存的 network_snapshot.json。但用户开启代理后，可能从家里 Wi-Fi 移动到办公室插入雷电扩展坞，或者中途开关过其他网络工具。数小时后点击“快照还原”，会把几小时前旧环境的 IP/代理配置强行刷回当前网卡，反而引发断网。

改进 1：用 Lima 原生映射替代裸 SSH

不要在 Dock App 里用脚本去跑 ssh -f -N -L 17890:...。直接在你的 Lima 实例配置文件（通常为 ~/.lima/<instance>/lima.yaml）中加入以下原生端口转发声明。这样只要 Lima 启动，宿主机 127.0.0.1:17890 就会由 Lima HostAgent 自动绑定并直通虚拟机内部代理端口，零 SSH 握手开销，且支持休眠唤醒秒级恢复。

改进 2：三模式热切换取代频繁改网卡

改进 3：彻底清网必须包含 DNS 与路由洗消

原方案的“核弹级重置”只关了 networksetup 的四个代理开关。但代理异常后最常见的是污染 DNS 缓存残留导致打不开国内网页或公司 VPN 认证页。重构后的核弹脚本会在关闭全网卡代理的同时，自动执行 dscacheutil -flushcache 与 killall -HUP mDNSResponder，并通过 macOS scutil --proxy 进行二次核验。
